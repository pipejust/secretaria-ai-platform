# Acten — Architecture Reference

Reference document for replicating the multi-tenant, branding/integrations, reports, and calendar/tasks modules in another project. Captures the data model, request lifecycle, isolation guarantees, and extension points as implemented today.

Stack: FastAPI + SQLModel/SQLAlchemy 2.x on Postgres 17 + pgvector, Angular 21 frontend, Coolify deployment behind Traefik.

---

## 1. Multi-Tenant Model

### 1.1 Tenant entity

Single `tenant` table is the root of every isolation chain. Every domain table that holds user data carries a `tenant_id INTEGER NOT NULL REFERENCES tenant(id)` column.

```text
Tenant
  id              PK
  slug            unique URL-safe id ("acten", "telar"…)
  name            display name
  domain          optional custom domain ("app.empresa.com")
  branding_json   JSON blob (logo, colors, company_website, …)
  landing_content_json  JSON for public landing CMS (only used by "acten")
  default_language      es | ca | en
  owner_user_id   FK user — first registered user, the only one that can flip the share switches
  share_integrations    bool — see §3
  share_routings        bool — see §3
  is_active       soft-delete flag
```

Models that propagate `tenant_id`:

```text
user, project, projectcontact (via project), meetingsession, actionitem,
integrationsetting, routing (via project), outputtemplate, sessionoutput,
apikey, auditlog, notification, askhistory, embeddingchunk (via session)
```

### 1.2 Tenant resolution in the request lifecycle

```
HTTP request
  ├── header `Authorization: Bearer <JWT>`
  │     → JWT decoded, `User` loaded by id, exposes user.tenant_id
  ├── header `X-Tenant-Slug: <slug>`  (frontend tenant.interceptor.ts)
  │     → consulted ONLY for unauthenticated public endpoints
  │       (/api/branding, /api/tenants/lookup, landing CMS public).
  │       For authenticated routes JWT wins.
  └── FastAPI dependency tree:
        get_current_user   → User from JWT
        get_current_tenant → db.get(Tenant, current_user.tenant_id)
        require_admin      → role.name == "admin" OR is_superadmin
        require_superadmin → is_superadmin only
```

Every protected endpoint declares both deps and applies the tenant filter:

```python
def list_projects(
    session: Session = Depends(get_session),
    tenant: Tenant = Depends(get_current_tenant),
    current_user: User = Depends(get_current_user),
):
    rows = session.exec(
        select(Project)
        .where(Project.tenant_id == tenant.id)
        .where(Project.is_active == True)
    ).all()
```

**Rule:** *every* table query must include `tenant_id == tenant.id`. No global-scope queries. The `_get_project_or_404`/`_get_session_or_404` helpers encapsulate this so leakage cannot regress.

### 1.3 Unique constraints — per-tenant compounds

The default `UNIQUE` constraints generated by SQLModel are tenant-blind and would conflict across tenants. The boot routine in `database._ensure_default_tenant_and_backfill` drops the legacy uniques and replaces them with `(col, tenant_id)` composites:

```text
uq_user_email_per_tenant            (email, tenant_id)
uq_project_name_per_tenant          (name, tenant_id)
uq_meetingsession_ff_per_tenant     (fireflies_id, tenant_id)
uq_outputtemplate_name_per_tenant   (name, tenant_id)
```

Special case for `integrationsetting` (per-user rows can coexist):

```text
uq_integration_tenant_global   (provider_name, tenant_id) WHERE user_id IS NULL
uq_integration_per_user        (provider_name, tenant_id, user_id) WHERE user_id IS NOT NULL
```

### 1.4 Superadmin & cross-tenant operations

`User.is_superadmin BOOLEAN`. The superadmin's JWT carries their own `tenant_id` (typically the founding tenant) — they don't impersonate. Cross-tenant admin endpoints (`/api/super/tenants`, `/api/super/branding`) require `require_superadmin` and accept `tenant_slug` as parameter to target another tenant.

Validation rules that depend on the tenant context (email-domain check, branding-website check) accept `skip_for_superadmin=admin_user` so the superadmin can create users in any tenant regardless of their JWT tenant.

### 1.5 Tenant provisioning flow

`POST /api/super/tenants` (superadmin):

1. Insert `Tenant` row (slug validated against `SLUG_RE`).
2. Insert admin `User` with `tenant_id = new tenant`, `role = admin`, hashed password.
3. Seed empty `IntegrationSetting` rows for the well-known providers so the settings UI is not empty.
4. Optionally seed default `Project`/`OutputTemplate`.
5. Soft-delete via `is_active=false` instead of physical delete to preserve audit trail.

### 1.6 Default-tenant boot fallback

If the DB starts empty (fresh deploy), `_ensure_default_tenant_and_backfill` creates a `tenant(slug="acten")`, then backfills `tenant_id` on every legacy table that was NULL, then promotes the first existing user to superadmin. This is the single migration path used in lieu of Alembic — kept idempotent so it runs every boot.

## 2. Branding Model

### 2.1 Storage shape

Branding is a single JSON column on `tenant.branding_json`. No relational table — values are sparse, evolve over time, and the frontend treats them as a flat key-value map.

```json
{
  "company_name": "Telar Support",
  "company_tagline": "...",
  "company_email": "contacto@telarsupport.com",
  "company_website": "https://telarsupport.com",
  "company_address": "...",
  "company_phone": "...",
  "primary_color":   "#0F172A",
  "secondary_color": "#EF2384",
  "accent_color":    "#4D14AF",
  "logo_data_url":      "data:image/png;base64,...",
  "logo_dark_data_url": "data:image/png;base64,...",
  "favicon_data_url":   "data:image/png;base64,..."
}
```

Logos are persisted as inline data URLs (base64). Pros: zero blob-storage dependency, deploys to anywhere. Cons: rows can hit 80–200 KB; clients keep this in memory. Acceptable for SaaS scale targeted (<10 MB per tenant). For larger assets switch the data URL for an object-storage path.

### 2.2 Endpoints

```text
GET    /api/branding                 public, requires `X-Tenant-Slug` header
PUT    /api/branding                 admin of the tenant
GET    /api/super/branding/{slug}    superadmin reading any tenant
PUT    /api/super/branding/{slug}    superadmin editing any tenant
```

The public `GET` exposes only safe keys (`company_name`, colors, logos, `default_language`, `company_website`). The full payload is admin-only.

### 2.3 Frontend application

`BrandingService` loads on app bootstrap → writes CSS variables (`--brand-primary`, …) on `:root` → all components consume those tokens. Logo light/dark variants choose which to render based on the active card background (see `branding-settings.component.html`).

### 2.4 `company_website` as authoritative SLD

The website field doubles as the tenant's canonical SLD. `_resolve_tenant_sld` returns `extract_sld(branding.company_website) || extract_sld(tenant.domain) || ""`. Used by `_validate_email_matches_tenant_domain` to gate user creation: only emails sharing the SLD are accepted (any TLD: `acten.app` accepts `@acten.co`, `@acten.net`, …). Superadmin bypasses.

## 3. Integrations Model

### 3.1 Two-axis design

Every integration provider falls in one of two categories:

| Category   | Stored as               | UI surface                       | Examples                              |
|------------|-------------------------|----------------------------------|---------------------------------------|
| per-tenant | `user_id IS NULL` row   | Settings → Integrations (admin)  | smtp/resend, fireflies, branding      |
| per-user   | `user_id IS NOT NULL`   | Settings → Integrations (self)   | trello, jira, clickup, azure, google, microsoft |

The frontier between the two is a frozen whitelist in `models.PER_USER_INTEGRATION_PROVIDERS`:

```python
PER_USER_INTEGRATION_PROVIDERS = frozenset({
    "trello", "jira", "clickup", "azure",
    "google", "microsoft",
})
```

### 3.2 IntegrationSetting row

```text
IntegrationSetting
  id           PK
  tenant_id    FK tenant  (NOT NULL)
  user_id      FK user    (NULL = per-tenant; NOT NULL = per-user)
  provider_name  e.g. "trello", "jira", "smtp", "fireflies"
  config_json  arbitrary JSON (api_key, token, board_id, …)
  is_active    bool
```

Two partial unique indexes guarantee that `(provider, tenant)` is unique among per-tenant rows AND `(provider, tenant, user)` is unique among per-user rows simultaneously (Postgres-only — see §1.3).

### 3.3 Share switches (tenant-level overrides)

The tenant owner can flip two independent switches at `tenant.share_integrations` / `tenant.share_routings`:

```text
share_integrations = true   → the owner's per-user credentials act as the
                              shared credentials for everyone in the team.
                              Non-owners see the config read-only with tokens
                              redacted ("***").
share_integrations = false  → every user manages their own (modes A above).

share_routings = true       → only the owner's routings exist per project;
                              everyone else sees them in read-only.
share_routings = false      → each user creates their own routings per project.
```

When share_* turns on, the per-user rows of non-owners are NOT deleted — they're hidden. Flipping back to off restores visibility (preserves data).

### 3.4 Endpoint matrix

```text
GET  /api/settings        per-tenant config (admin)
POST /api/settings        save per-tenant (admin, rejects per-user providers)
GET  /api/settings/me     per-user config of current_user
                          if share_integrations + non-owner → returns owner's
                          config with sensitive keys redacted to "***"
POST /api/settings/me     save per-user (403 if share_integrations + non-owner)
DELETE /api/settings/me/{provider}   disconnect (403 if locked)
GET  /api/settings/share  always allowed — returns {owner_user_id, is_owner,
                          share_integrations, share_routings}
PUT  /api/settings/share  owner-only — flip the two switches
```

### 3.5 Routing (destination per project)

```text
Routing
  id PK
  project_id    FK project
  user_id       FK user  (per-user even when project is shared)
  destination_type    "trello" | "jira" | "clickup" | "azure" | "slack" | …
  destination_config  JSON ({board_id, list_id} | {project_key} | …)
  is_active     bool
```

Endpoints follow the same per-user / share-routings logic:

```text
GET    /api/projects/{pid}/routings              list (respects share_routings)
POST   /api/projects/{pid}/routings              create (403 if not owner when ON)
PUT    /api/projects/{pid}/routings/{rid}        edit destination_type / config
DELETE /api/projects/{pid}/routings/{rid}        delete
PATCH  /api/projects/{pid}/routings/{rid}/toggle is_active
```

`_get_routing_for_user_or_404` returns 404 (not 403) when the routing doesn't belong to the current effective owner — this prevents leaking the existence of another user's routing.

### 3.6 Dispatch (sending tasks to external platforms)

Two entry points:

- Auto-dispatch on Fireflies webhook completion (`process_transcript_background` in `routers/fireflies.py`).
- Manual dispatch button (`POST /api/sessions/{id}/dispatch_platforms` in `routers/sessions_upload.py`).

Both resolve routings via `_routings_for_project_dispatch(db, project_id)` which respects `share_routings`. For each routing the credentials are loaded via:

```python
creds_user_id = (
    tenant.owner_user_id if tenant.share_integrations and tenant.owner_user_id
    else routing.user_id
)
get_service_for_destination(db, dest_type, tenant_id=…, user_id=creds_user_id)
```

`services/integrations/__init__.py::get_service_for_destination` is the single factory: it switches on `dest_type` and returns a configured client class (`TrelloIntegrationService`, `JiraIntegrationService`, etc.). Adding a provider means adding the service class and one branch in the factory + an entry in `PER_USER_INTEGRATION_PROVIDERS` if user-scoped.

## 4. Reports Model

### 4.1 Source of truth

Reports are *computed on demand* from the operational tables — no precomputed `report` rows. Inputs:

```text
MeetingSession   (status, language, raw_summary, processed_decisions,
                  processed_risks, processed_agreements, processed_attendees,
                  date, project_id, …)
ActionItem       (title, owner_email, status, due_date, completed_at,
                  priority, session_id, tenant_id)
Project          (name, description, owner_user_id, language_code)
ProjectContact   (name, role, entity, email)
```

### 4.2 Time-window resolver

`_resolve_window(query)` accepts:

- `range=last_7d|last_30d|this_month|last_month|this_quarter|custom`
- `from=YYYY-MM-DD`, `to=YYYY-MM-DD` (only for `range=custom`)

Returns a `(start, end)` tuple in UTC. All downstream queries filter `session.date` and `actionitem.due_date|completed_at` against this window.

### 4.3 `_build_report(db, tenant_id, window, project_id?)`

The single orchestration function. Composes the response payload:

```text
{
  "kpis": {
    "sessions_total":   N,
    "sessions_done":    N,
    "decisions_total":  N,
    "actions_total":    N,
    "actions_done":     N,
    "actions_overdue":  N,
    "avg_duration_min": float,
    "completion_pct":   0-100,
  },
  "projects": [
    { id, name, sessions_count, items_total, items_done,
      progress_pct, classification, top_owner, last_session_date }
  ],
  "decisions_timeline": [ { date, project, text, source_session_id } ],
  "owner_leaderboard":  [ { email, name, items_total, items_done,
                            avg_close_days } ],
  "risk_register":      [ { project, risk_text, sessions } ],
  "filters_used": { range, from, to, project_id }
}
```

Key helpers:

- `_classify_project_by_sessions(sessions)` → `{ active | dormant | stalled | closed }` based on recency + status mix.
- `_project_progress_pct(items)` / `_project_progress_pct_by_sessions(sessions)` — two strategies depending on whether the report views by tasks or sessions.
- `_top_owner_for_project(items)` — most-assigned email.

### 4.4 Endpoints

```text
GET /api/reports/data    JSON payload as above (frontend dashboards)
GET /api/reports/pdf     reportlab/weasyprint render — single PDF
GET /api/reports/excel   openpyxl multi-sheet workbook
                         (KPIs, Projects, Decisions, Tasks, Owners, Risks)
```

PDF/Excel reuse `_build_report` to ensure consistency. Both attach the tenant's branding (logo, primary color) so reports are white-labelable.

### 4.5 Multi-tenant guarantee

Every query inside `_build_report` filters `MeetingSession.tenant_id == tenant_id` and `ActionItem.tenant_id == tenant_id` explicitly — *don't* rely on `ActionItem.session.tenant_id` joins; tasks carry a redundant `tenant_id` for defense-in-depth.

### 4.6 Extension points

Add a new KPI: extend the `kpis` dict in `_build_report` + add a column to the PDF/Excel writers. The shape stays flat so the frontend doesn't need restructuring.

## 5. Calendar Process

### 5.1 Data model

Calendar is per-user OAuth, not per-tenant:

```text
CalendarAccount
  id PK
  user_id          FK user
  provider         "google" | "microsoft"
  account_email    the email the OAuth flow returned
  access_token     encrypted in prod, plaintext in dev
  refresh_token    used by `CalendarService.refresh_if_needed`
  token_expires_at ISO
  scopes           space-separated
  is_active        bool

CalendarEvent
  id PK
  calendar_account_id  FK
  external_id          provider's native event id
  title, start_at, end_at
  attendees_json       JSON array
  meeting_url          Zoom/Meet URL if present
  project_id           optional FK project — set by the auto-match heuristic
  session_id           FK meetingsession — populated when the recording acta
                       arrives via Fireflies webhook, linking event ↔ session
```

### 5.2 OAuth flow

```text
1. GET  /api/calendar/{provider}/auth_url
      → builds the consent URL using IntegrationSetting('google_calendar') /
        ('microsoft_calendar') of the tenant (client_id, redirect_uri, scopes).

2. (user consents, provider redirects to backend)
   GET  /api/calendar/{provider}/callback?code=…&state=…
      → exchanges code for tokens, persists a CalendarAccount row for the
        current_user.

3. GET    /api/calendar/accounts        list user's connected accounts
   DELETE /api/calendar/accounts/{id}   revoke (clears tokens, sets inactive)

4. POST  /api/calendar/sync             pull events for current_user
                                         (calls services.calendar_service)
5. GET   /api/calendar/upcoming         events of current_user for date range
```

`oauth_config_status` returns `{google: {ready, source}, microsoft: {ready, source}}` indicating whether the tenant has env-level fallback OR a tenant IntegrationSetting configured.

### 5.3 `services/calendar_service.py`

Wraps Google Calendar API and Microsoft Graph. Public surface:

- `refresh_if_needed(account)` — checks `token_expires_at`, refreshes when within 5 min.
- `pull_events(account, start, end)` — paginated; upserts into `CalendarEvent` by `(account_id, external_id)`.
- `attach_session(event_id, session_id)` — called by the Fireflies webhook handler when a new `MeetingSession` matches an existing event by `meeting_url` or `start_at` proximity.

### 5.4 Cron jobs (`services/cron_service.py`)

```text
sync_calendars()      every 15 min  — refresh + pull for every active account
check_upcoming()      every 5 min   — emits Notification when an event is
                                      starting within N minutes (per user prefs)
auto_dispatch_tick()  every 5 min   — see §6.5
```

Job runtime: a single FastAPI startup spawns an `asyncio.create_task` loop that pings each handler at its cron. No external worker.

## 6. Tasks Process

### 6.1 ActionItem entity

```text
ActionItem
  id PK
  tenant_id     FK tenant
  session_id    FK meetingsession   (each task belongs to ONE session)
  title         short
  description   long
  owner_name    inferred by LLM ("Felipe Cortés")
  owner_email   matched against project_contacts/users (see §6.3)
  due_date      YYYY-MM-DD
  due_time      HH:MM (optional)
  priority      "alta" | "media" | "baja"
  status        "pending" | "in_progress" | "done" | "not_started"
  completed_at  ISO when status flips to done
```

### 6.2 Generation pipeline

`services/transcript_pipeline.py::process_session_with_ai(db, session_id)`:

```text
1. Load MeetingSession + transcript.
2. Detect project from title/transcript (auto-match), or use existing project_id.
3. Load project_contacts of that project (canonical contacts the admin
   maintained).
4. Groq.process_fundamentals_and_insights(transcript, project_contacts,
   output_language=tenant_lang)
       → returns { language, summary?, decisions, risks, agreements,
                   attendees, themes, action_items }.
5. Persist insights into MeetingSession (raw_summary, processed_decisions,
   processed_risks, processed_agreements, processed_themes,
   processed_attendees).
6. For each action_item from the LLM:
     - title, description, owner_name, owner_email, due_date, due_time,
       priority
     - run _resolve_owner_email(owner_name, llm_email) — see §6.3.
     - insert ActionItem row with tenant_id, session_id linkage.
7. Set session.status = "pending" (ready for human curation) +
   processing_completed_at = now.
```

If any step throws, the orchestrator records the error in `session.processing_error` and increments `processing_attempts`. A daily cron retries failed sessions and triggers `_send_session_ready_email` (see §6.6).

### 6.3 Owner email resolution

Multi-tier match — described in `_resolve_owner_email`:

```text
1. If LLM already provided an email with "@" → trust it.
2. Build canonical name → email lookup:
     project_contacts (primary, admin-curated)
     + processed_attendees (speakers who actually spoke).
3. Lookup canon(owner_name) in that table.
4. If "Por asignar" / "Unknown" / "" → leave email empty.
```

Speaker-to-contact canonical match has three precision tiers (`_merge_speakers_with_groq_attendees`):

```text
a. Full canonical name match (most precise, no ambiguity).
b. First-name token ∩ last-name match — unique candidate.
c. Last-name only — unique candidate of that surname.
d. Otherwise keep the transcript spelling, no enrichment.
```

### 6.4 Curation panel

`POST /api/sessions/{id}/regenerate_tasks` and `/regenerate_fields` re-run the LLM extraction without re-running speaker enrichment. UI in `curation-panel.component.ts` allows manual edits to:

```text
- raw_summary, processed_decisions, processed_risks, processed_agreements
- project_id (with "update all components?" modal that triggers a retry of
              the pipeline scoped to the new project's contacts)
- each ActionItem: title, description, owner_email, due_date, status, priority
```

### 6.5 Auto-dispatch

A project can be configured to auto-send tasks to external platforms when:

- Pipeline finished successfully (`processing_completed_at != ""`, `processing_error == ""`).
- All tasks have an `owner_email`.
- Project flag `auto_dispatch_enabled = true`.
- Time-since-session > `auto_dispatch_timeout_hours` (default 1, configurable per-project).

The cron tick (`services/cron_service.auto_dispatch_tick`):

```text
for session in pending_completed_sessions:
    if not project.auto_dispatch_enabled: continue
    if missing owner emails:
        notify_admins("session_needs_emails"); set blocked_reason; continue
    fire dispatch_platforms for that session.
```

### 6.6 Notifications

After the AI pipeline finishes, the session emits:

```text
1. session_ready email  → owners + (if project) project members; else admins.
2. notify_admins_session_processed in-app → same recipients.
3. Per-item assignment emails (optional) when a task has owner_email.
```

`_resolve_admin_recipients(db, tenant_id, project_id)` and `notify_admins(..., project_id=…)` scope the audience:

```text
project_id given → users matching project.owner_user_id + ProjectContact.email
                   matched to User.email. Fallback to admins if list empty.
project_id None  → tenant admins.
```

### 6.7 Dispatch to externals

Already described in §3.6.

## 7. Cross-cutting infrastructure

### 7.1 Audit

`AuditLog` rows are written by `services/audit.py::audit_event(db, tenant_id, user_id, action, resource_type, resource_id, payload_diff)`. Indexed by `(tenant_id, action)` and `(created_at)`. Reviewed via `/api/super/audit` (superadmin only).

### 7.2 Notifications (in-app)

`Notification(user_id, tenant_id, kind, title, body, link_to, entity_type, entity_id, is_read, created_at)` — fanout via `notify_user` / `notify_admins` / `notify_admins_session_processed`. Dedup window: 24 h by `(user_id, kind, entity_type, entity_id)` to avoid spam from retried crons. Fed to the bell icon by `GET /api/notifications`.

### 7.3 i18n

Backend resolves `output_language` from `User.language || Tenant.default_language || "es"`. The LLM gets the language label injected ("Español", "Català", "English") so structured output (summary, decisions, …) is always in the target. Frontend uses `@ngx-translate/core` with JSON dictionaries at `frontend/public/assets/i18n/{es,en,ca}.json` (Angular 17+ uses `public/`, **not** `src/assets/`).

### 7.4 Database migrations

No Alembic. The startup function `database._apply_lightweight_migrations()` executes a list of idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS` statements every boot. Cheap and always converges. For data backfills, `_ensure_default_tenant_and_backfill()` runs once per boot and is gated by row-existence checks.

### 7.5 Embeddings (RAG)

`EmbeddingChunk(session_id, kind, content, embedding_vector vector(1536))` — chunked by `kind` (summary, decisions, risks, agreements, transcript, themes, attendees, keyword:<name>). Indexed with `ivfflat (vector_cosine_ops)`. Queries always filter `session.tenant_id == current_tenant.id` joined through `session_id` to enforce multi-tenant isolation in semantic search.

## 8. Dashboard

### 8.1 Concept

Two layers of dashboards exist:

- **Tenant-wide dashboard** (`/admin/dashboard`) — global overview for the current user: meetings, pending tasks, integrations health, ROI.
- **Project dashboard** (`/admin/projects/:id`) — narrowed to a single `project_id`: contacts, recent sessions, decisions, active tasks, metrics.

Both follow the same pattern: **no precomputed `dashboard_snapshot` rows; the data is composed on-demand from the operational tables.** Snapshots get stale; on-demand stays consistent at the cost of a few extra round-trips per page load.

### 8.2 Data sources per widget

```text
Widget                          Source endpoint                          Table(s)
─────────────────────────────────────────────────────────────────────────────────
Recent meetings list            GET /api/sessions/?page=1&limit=50       MeetingSession
Meeting KPIs (totals/avg)       GET /api/sessions/_stats                 MeetingSession
Pending tasks list              GET /api/pendientes                      ActionItem
Pending tasks counters          GET /api/pendientes/stats                ActionItem
Sync Health (Trello/Jira/…)     GET /api/settings (admin)                IntegrationSetting
                                + GET /api/settings/me                   (per-user provs)
Active projects list            GET /api/projects                        Project
ROI executive panel             GET /api/analytics/roi                   MeetingSession+ActionItem
Recurring meetings              GET /api/analytics/recurring             MeetingSession
Notifications bell              GET /api/notifications                   Notification
Calendar upcoming               GET /api/calendar/upcoming               CalendarEvent
Project detail dashboard        GET /api/projects/{id}/dashboard         Project+Session+Action+Contact+Routing
```

Frontend `dashboard.component.ts` fires these in parallel from `ngOnInit` (no waterfalls).

### 8.3 Tenant-wide endpoints

#### `GET /api/sessions/_stats`

Aggregated KPIs across **all** sessions for the tenant — explicitly tenant-scoped, not paginated. Returns:

```text
{
  total,                  # COUNT(*) WHERE tenant_id = :t
  analyzed,               # COUNT WHERE status = 'completed'
  pending,                # COUNT WHERE status = 'pending'
  archived,               # COUNT WHERE status = 'archived'
  avg_duration_minutes,   # AVG(length(raw_transcript)/900.0)
}
```

Filters allowed: `project_id`, `include_archived`. Does NOT accept `status` or `search` — KPIs reflect the universe, not the active UI filter.

#### `GET /api/pendientes/stats`

ActionItem counters bucketed by classification function `_classify(item, now)`:

```text
{
  counts: {
    vencido, proximo, pendiente, sin_fecha,
    bloqueado, completado, cancelado,
  },
  active_total,                # vencido + proximo + pendiente + bloqueado + sin_fecha
  top_owners_active: [ {owner, count} ]   # top 10
}
```

Tenant-scoped via `ActionItem.tenant_id == tenant.id`.

#### `GET /api/analytics/roi`

Executive ROI panel. Estimates meeting minutes from transcript word count (150 wpm proxy) and computes completion rates. **Note: this endpoint currently does NOT filter by tenant_id — pending fix.** New consumers must scope manually or wait for the fix.

### 8.4 Project-dashboard endpoint

`GET /api/projects/{project_id}/dashboard`:

```text
{
  project: { id, name, description, is_active, owner_user, auto_dispatch_*  },
  metrics: {
    total_sessions, active_action_items, overdue,
    upcoming_7d, completed_action_items,
    contacts_count, routings_active,
  },
  last_sessions:       [ … 10 most recent ],
  recent_decisions:    [ … last 5 sessions with decisions ],
  active_action_items: [ … sorted (overdue → upcoming → other) ],
  contacts:            [ … project_contacts ],
}
```

Sorting of `active_action_items`:

```python
key = (
    0 if is_overdue else 1 if is_upcoming else 2,   # bucket priority
    due_date or "9999-12-31",                       # then chronological
)
```

Time logic:

```text
overdue   → due_date < now AND status NOT IN (done, cancelled)
upcoming  → due_date in [now, now + 7 days]
```

Multi-tenant: `_get_project_or_404` rejects access to projects of other tenants, then every nested query (`MeetingSession`, `ActionItem`, `ProjectContact`, `Routing`) filters on `tenant.id` / `project_id` for defense-in-depth.

### 8.5 Frontend orchestration

`dashboard.component.ts` keeps separate state slots:

```ts
sessions: any[];           // latest sessions
allActionItems: any[];     // /api/pendientes
integrations: any = {};    // /api/settings → Sync Health card
projects: any[] = [];
kpiStats: any = null;      // /api/sessions/_stats
pendingStats: any = null;  // /api/pendientes/stats
```

Each loader is **independent** and emits `cdr.detectChanges()` on completion so the panel paints progressively (no full-screen spinner that blocks until everything arrives). Errors per loader degrade gracefully — failure in one widget doesn't kill the others (e.g. Sync Health 403 for non-admin → card hidden, rest of the dashboard still renders).

### 8.6 Customization & extension points

- **New KPI tile:** add a counter to `_stats` (or `_pendientes/stats`) + render in `dashboard.component.html`. Keep the response shape flat so the frontend doesn't restructure.
- **New widget:** mint a new tenant-scoped endpoint (always require `Depends(get_current_tenant)`). Add a slot + loader in `dashboard.component.ts`. Don't read from another component's state — every widget owns its own load.
- **Snapshot caching:** if dashboard cold-load becomes too slow at scale, the right cache point is the `_stats` endpoints (server-side, per-tenant, 60 s TTL via Redis). The on-demand pattern stays correct; only the heavy aggregations get cached.

### 8.7 Multi-tenant guarantee for dashboards

Every dashboard endpoint declares `tenant: Tenant = Depends(get_current_tenant)`. Every aggregation includes `WHERE table.tenant_id = tenant.id` — never via the FastAPI dep alone. This is enforced by repeated `tenant_id` columns on derived tables (e.g. `ActionItem.tenant_id` is redundant with `ActionItem.session.tenant_id`, kept on purpose so a wrong join cannot leak data).

Pitfall to avoid (currently present in `/api/analytics/roi`): aggregations that do `select(Model)` without `where(tenant_id ==)`. Always filter at the lowest table.
